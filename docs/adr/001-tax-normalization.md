# ADR 001: 税抜・税込混在レシートの品目価格正規化

## Status

Accepted

## Context

仕様書では `items[].price` を税込の行合計とし、その合計とレシート合計を
±2円で照合する。一方、日本のレシートには税抜価格へ外税を後加算する商品と、
内税価格の商品が同時に記載される場合がある。

合計差額だけを税とみなす補正は、読み落とした商品を税と誤認して
`confirmed` にする危険がある。また、内税を一律加算すると二重計上になる。

## Decision

- VLM出力に、品目の印字価格、税率、内税・外税区分と、レシート記載の
  税率別内訳を追加する。
- 印字価格は `price_raw`、正規化後の税込価格は既存の `price` に保持する。
- 外税補正は、同じ税率の品目印字額合計、または品目印字額合計と外税額の和が、
  レシート記載の外税対象額と±2円で一致する場合に限る。レシートにより
  税率別対象額が税抜・税込のどちらで表示される場合にも対応する。
- 品目の税率が不明な場合は、品目印字額の部分集合と税率別対象額を照合する。
  部分集合は金額だけでなく、元配列上の品目インデックスの組み合わせとして
  保持する。同額商品も別の組み合わせとして扱う。
- 8%と10%を含むすべての有効な外税候補を同時に探索し、同じ品目を複数税率へ
  割り当てない。税率ごとに先に一意性を決めず、全体割当として一意かを判定する。
- 候補となる外税額の組み合わせを補正前の品目合計へ加え、レシート合計との差が
  最小の組み合わせを求める。自動補正は最小誤差が0円で、かつ同率の最良割当が
  1件だけの場合に限る。±2円は対象額の印字・端数照合だけに使い、補正後合計の
  採用条件には使わない。
- 部分集合探索と全体割当探索は、税率、対象額、税額、品目インデックスを
  明示的にソートした順で行う。Pythonの集合・辞書の反復順へ結果を依存させない。
- 部分集合探索が20,000状態、外税内訳が8件を超える場合は補正せず、
  計算量の増大と誤確定を避ける。上限到達は例外にせず補正拒否として扱う。
- レシート記載の外税額を品目印字額に比例配賦し、余りは端数の大きい順、
  同値なら品目順で1円ずつ配る。
- 内税品は外税候補から除外する。値引き行は負数のまま部分集合へ含められるが、
  値引きを含む割当と含まない割当が同精度なら曖昧として拒否する。
- 税率は8%または10%に限定し、対象額と税額は非負であることを要求する。
  明示税額が対象額と税率から説明できない候補は除外する。負数や非対応税率など
  入力自体が矛盾する場合は、補正全体を拒否する。
- 内訳不足、対象額不一致、曖昧性、探索上限到達では推測補正せず、
  `price_raw`をそのまま`price`へ保持して`review`とする。合計差額から
  新しい税額や税内訳を生成しない。
- SQLiteでは既存の `items.price` を正規化済み価格として維持し、
  監査用情報を別テーブルへ保存する。

## Automatic correction acceptance conditions

次の条件をすべて満たす場合だけ自動補正を採用する。

1. VLMが税率別対象額と外税額を明示している。
2. 対象額と±2円で一致する品目インデックスの組み合わせが存在する。
3. 全税率候補を同時に考慮した割当が一意である。
4. 同じ品目を複数税率へ割り当てていない。
5. 補正後の税込品目合計がレシート合計と完全一致する。
6. 他の外税候補を含む全組み合わせより誤差が小さい。
7. 同率の最良候補が複数存在しない。
8. 探索状態数と外税グループ数が設定上限以内である。
9. 採用する税情報に負数、非対応税率、税率計算との矛盾がない。

いずれかを満たさない場合は、部分的な補正も採用せず元の印字価格を保持する。

## Auditability

- `receipt_tax_breakdowns`にVLMが明示した税率、対象額、税額、内外税区分を保存する。
- `items`のレシート内順序と`item_tax_details`の`price_raw`、`tax_rate`、
  `tax_adjustment`、および`items.price`から、割当品目インデックスと配賦結果を
  再構成できる。
- 補正拒否理由と探索上限到達は、`validation_issues_json`へ
  `tax.normalization.*`コードとして保存する。
- 上記の既存テーブルで、補正実行の有無、入力税情報、割当、補正前後、採否理由を
  説明できるため、この監査強化では新しいマイグレーションを追加しない。

## Consequences

- 既存のJSONフィールドとSQLite列は維持される。
- 税メタデータを出さない旧Ollama応答も読み取れるが、外税を安全に補正できない
  場合は従来どおり `review` になる。
- レポートは既存の `items.price` を集計すれば税込金額を利用できる。
- 安全性を優先するため、数値上は補正できそうでも全体割当が曖昧なケースや、
  補正後合計が1〜2円ずれるケースは`review`になる。
