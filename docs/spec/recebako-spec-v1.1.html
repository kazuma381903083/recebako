01

概要

1-1目的

レシートを「撮るだけ」で家計簿が完成する仕組みを作る。手入力・手動アップロード・費目の手選択を全廃し、月次の支出レポートまで全自動で生成する。同時に、VLM（画像が読めるLLM）＋構造化出力という2026年の中核技術を、実際に毎日動くシステムを通して習得する。

  • 処理サーバ：Apple M1 Pro/Max・メモリ32GB・Ollama導入済み・常時起動でなくてもよい（起動時にまとめて処理する設計とする）

02

最重要の設計判断 — 画像をどうやってMacに運ぶか

本システムで最初に決めるべき最大の論点。「Googleフォトを使ってるからGoogleフォトのAPIで取ればいい」と考えたくなるが、2025年の仕様変更でその道はほぼ塞がれている。

前提となる事実（2025年3月31日発効）：Google Photos Library APIから photoslibrary.readonly 等のスコープが削除され、アプリはユーザーのライブラリ全体を読めなくなった（読めるのは自アプリが作成した写真のみ。旧スコープでの呼び出しは403）。全体からの取得は、ユーザーがその都度手で写真を選ぶ「Picker API」に置き換えられた。つまり「Googleフォトに上がった新着レシートを自動で吸い出す」個人アプリは公式には作れない。

2-13案の比較検討

案仕組み自動化セキュリティ実装難度評価
A. Google Photos
Picker API		OAuth＋セッション作成→ユーザーがフォトアプリで選択→アプリが取得✕ 毎回手動選択△ Google経由高(OAuth/ポーリング)「撮るだけ」の目的に反する。不採用
B. Google Takeoutライブラリ一括エクスポートをDL✕ バッチのみ△低過去レシートの初期移行専用で採用
C. Syncthing
直接同期		Pixel⇄MacをP2Pで直結し、専用フォルダをリアルタイム同期。クラウドを一切経由しない◎ 完全自動◎ LAN内完結低◎ 本採用
SyncthingはOSSのファイル同期ツール（Dropboxのサーバ無し版）。端末同士が直接暗号化通信（TLS）でフォルダを同期する。AndroidアプリとMac版を入れ、互いの「デバイスID」を承認し合うだけで動く。サーバも登録も不要。

2-2採用構成と運用ルール

  1. Pixel側に Receipts/ フォルダを作り、Syncthingで Mac の ~/recebako/inbox/ と同期する（送信専用設定）。
  2. レシートは標準カメラで撮影 → 共有メニューから Receipts/ へ保存（1タップ）。慣れたら「カメラ→共有→Receipts」がレジ前の3秒作業になる。
  3. Googleフォトのバックアップ対象に Receipts/ を含めない（フォトの設定で該当フォルダのバックアップをOFF）。これによりレシート画像はGoogleのクラウドに一切上がらない。購買履歴という機微データの露出面を構造的に消す。
  4. 通常のカメラフォルダで撮ってしまった分は、月次でTakeout経由 or 手動move（救済経路）。
この判断の意味：「Googleフォト対応」を“Googleフォトと共存しつつ、レシートだけはその外側で完全ローカルに流す”と定義し直した。普段の写真は今まで通りGoogleフォトへ、レシートはSyncthingでMac直行。APIの制約回避とセキュリティ向上が同じ一手で達成できる。

05

データ設計

5-1抽出JSONスキーマ — システムの心臓部

VLMの出力をこのスキーマに強制する（Ollamaのformatパラメータに渡す）。自由文を一切許さないことで後段が壊れなくなる。

{
  "type": "object",
  "required": ["store", "date", "total", "items", "confidence"],
  "properties": {
    "store":      {"type": "string",  "description": "店名。読めなければ空文字"},
    "date":       {"type": "string",  "description": "YYYY-MM-DD。読めなければ空文字"},
    "time":       {"type": "string"},
    "items": {
      "type": "array",
      "items": {"type": "object",
        "required": ["name", "price"],
        "properties": {
          "name":  {"type": "string"},
          "qty":   {"type": "integer", "default": 1},
          "price": {"type": "integer", "description": "円・税込の行合計"}}}
    },
    "subtotal":   {"type": "integer"},
    "tax":        {"type": "integer"},
    "total":      {"type": "integer", "description": "レシート記載の合計金額"},
    "payment":    {"type": "string",  "enum": ["cash","credit","qr","emoney","unknown"]},
    "confidence": {"type": "number",  "description": "読み取り自信度 0.0-1.0"}
  }
}
「読めない項目は空文字や0で埋めさせる」のがコツ。無理に埋めさせると幻覚（それっぽい嘘）が混入する。confidenceを自己申告させ、低いものは要確認行きにする。

5-2SQLiteテーブル定義

CREATE TABLE receipts (
  id          INTEGER PRIMARY KEY,
  store       TEXT, date TEXT, time TEXT,
  total       INTEGER, subtotal INTEGER, tax INTEGER,
  payment     TEXT,
  category    TEXT,                  -- 費目(レシート単位の主費目)
  status      TEXT NOT NULL,         -- confirmed / review / failed
  confidence  REAL,
  phash       TEXT,                  -- 重複検出用
  image_path  TEXT NOT NULL,         -- 原本画像への相対パス
  created_at  TEXT DEFAULT (datetime('now','localtime'))
);
CREATE TABLE items (
  id INTEGER PRIMARY KEY, receipt_id INTEGER REFERENCES receipts(id),
  name TEXT,                       -- レシート記載の生の品目名(原本保持)
  name_norm TEXT,                  -- 正規化名(「ｷｬﾍﾞﾂ1/2」→「キャベツ」)。品目集計はこちらで行う
  qty INTEGER, price INTEGER, category TEXT
);
CREATE TABLE store_master (      -- 店名→費目の学習マスタ(修正が溜まるほど賢くなる)
  store_pattern TEXT PRIMARY KEY, category TEXT, updated_at TEXT
);

5-3フォルダ構成と状態遷移

~/recebako/
├── inbox/          ← Syncthing着信(未処理)
├── processing/     ← 処理中(クラッシュ時の再開判定に使う)
├── archive/2026/08/ ← 処理済み原本(年月別・改名済み)
├── review/         ← 要確認(レビューUIの対象)
├── failed/         ← 3回失敗(画像不良など。人間が見る)
├── ledger.db       ← SQLite本体
└── reports/2026-08.html

状態遷移:  inbox → processing → ┬→ confirmed(archive/ + DB確定)
                                ├→ review  (自信度低・整合NG)
                                └→ failed  (抽出3回失敗)

※ フォルダ＝状態にすると、DBを開かなくてもlsで系の健全性がわかる。障害対応でログとキューを最初に見る癖のある人間には馴染む設計のはず。

6-2検証ロジック — 「三値管理」で品質を作る

VLMの出力を信用せず、機械検証を通す。品質はモデルではなく検証で作るのが本仕様の思想。決済の三値管理と同じで、「成功/失敗」の間に「不明(要確認)」を明示的に置く。

検証項目ルールNG時の判定
合計整合Σ(items.price) と total の差が ±2円以内（端数処理誤差を許容）review
日付妥当性date が過去1年以内の実在日付review
自信度confidence ≥ 0.8review
重複pHash距離が近い既存画像なし、かつ (store,date,total) の完全一致なしreview(重複疑い)
抽出成功JSONパース成功かつ必須項目あり。失敗時は画像を回転/拡大して最大3回再試行3回失敗で failed

6-3費目分類 — 2段構え

  1. 店名マスタ優先：store_masterに一致があれば即決（LLM不要・0ms・ブレなし）。
  2. マスタに無い店だけLLM：店名＋品目リストを渡し、費目enumから1つ選ばせる（temperature=0）。ユーザーがレビューUIで直したらマスタに書き戻し、同じ店で二度と間違えない。
設計思想：LLMは「初見の判断」だけに使い、確定した知識はマスタ（ただのテーブル）に降ろす。呼び出し回数が減る＝速く・安定し、挙動が説明可能になる。AIシステムを運用に耐えさせる基本パターンで、業務でもそのまま使える考え方。

6-4品目正規化とレポート用集計SQL（v1.1追加）

「費目の中の品目ごとの集計」を成立させる鍵は品目名の正規化。レシートの生表記（ｷｬﾍﾞﾂ1/2、ﾄﾘﾑﾈ、ｻﾝﾄﾘｰ金麦6P）のままでは同じ物が別品目として散らばる。抽出時にLLMへ「一般名詞への正規化」も同時にやらせ、items.name_normに格納する（生表記はnameに原本保持）。

# 抽出プロンプトへの追記(6-1のルールに追加)
6. 各品目に name_norm を付ける: 記号・容量・規格を除いた一般名
   (例:「ｷｬﾍﾞﾂ1/2」→「キャベツ」/「ﾄﾘﾑﾈ 2kg」→「鶏むね肉」)。
   固有ブランドは種類名に寄せる(「金麦6P」→「ビール(6缶)」)
-- (a) 日別出費推移(費目積み上げグラフの元データ)
SELECT r.date, i.category, SUM(i.price) AS amount
FROM items i JOIN receipts r ON r.id = i.receipt_id
WHERE r.status = 'confirmed' AND r.date LIKE '2026-08-%'
GROUP BY r.date, i.category ORDER BY r.date;

-- (b) 費目内の品目別集計(回数・合計・平均単価)
SELECT i.category, i.name_norm,
       COUNT(*)      AS 回数,
       SUM(i.price)  AS 合計,
       SUM(i.price)/COUNT(*) AS 平均単価
FROM items i JOIN receipts r ON r.id = i.receipt_id
WHERE r.status = 'confirmed' AND r.date LIKE '2026-08-%'
GROUP BY i.category, i.name_norm
ORDER BY i.category, 合計 DESC;

※ レポートHTMLはこの2本のSQL＋店舗集計だけで組み立てられる。グラフは外部ライブラリを使わず、Pythonで座標計算したSVGを埋め込む方式（オフライン完結・NFR-S1準拠）。実物の見た目はサンプルレポート「recebako-report-sample.html」を参照。

非機能要件（NFR）— 性能・品質・セキュリティ・保守

7-1性能要件

ID項目目標値測定方法
NFR-P11枚あたり処理時間撮影→DB登録まで 60秒以内（うちVLM抽出30秒以内）処理ログのタイムスタンプ
NFR-P2バッチ処理能力溜まった50枚を30分以内（Mac起動時の一括処理を想定）実測
NFR-P3リソース占有VLM常駐メモリ7GB以下。他作業と同居可能なこと。アイドル時はモデルをアンロードollama ps / Activity Monitor

※ VLM速度の実測は「性能測定手順書」の方法をそのまま使う。処理時間が目標を超える場合の緩和策はQwen3-VL 4Bへの切替（8-3参照）。

7-2品質要件 — 数値で定義する

ID項目目標備考
NFR-Q1合計金額の抽出精度98%以上（ゴールデンセット30枚）家計簿の生命線。最優先
NFR-Q2店名・日付の抽出精度95%以上表記ゆれは正規化後に判定
NFR-Q3品目レベルの抽出精度80%以上v1では参考情報の位置づけ
NFR-Q4誤確定率「confirmed判定なのに合計が誤り」が2%以下検証すり抜けの監視指標
NFR-Q5要確認率30%以下（運用が回る上限）高すぎたらプロンプト/モデル見直し

※ NFR-Q1〜Q5の再現可能な分母、店名の比較正規化、 raw品目tupleの順序保持alignment、0分母、30件未満の扱いは ADR 002の quality-v1で固定する。既存評価reportとstdoutのschema version 1は 変更せず、品質判定はaggregate-onlyの独立sidecarへ記録する。30件すべてが 人間確認済みになるまでは観測rateを目標達成判定として扱わない。

7-3セキュリティ要件

ID項目要件
NFR-S1データ境界レシート画像・抽出データ・DBはインターネットに送信しない。通信はSyncthingのP2P（TLS・デバイスID相互承認済み端末のみ）に限定
NFR-S2クラウド排除Receipts/フォルダをGoogleフォトのバックアップ対象から除外し、レシートがGoogle側に複製されない構成を維持する
NFR-S3ログ衛生ログに品目・金額等の内容を出力しない（ファイル名・状態・所要時間のみ）。デバッグ出力は開発時フラグでのみ有効
NFR-S4保存時保護Mac側はFileVault(ディスク暗号化)有効を前提。バックアップはTime Machine等ローカルのみ
NFR-S5レビューUI127.0.0.1バインドのみ（LAN公開しない）。認証不要の代わりに外部到達性ゼロで担保
NFR-S6依存の健全性依存パッケージは最小限とし、四半期ごとに脆弱性確認（pip-audit）。モデルはHugging Face公式リポジトリからのみ取得

7-4可用性・保守性

  • 再開性：どの段階でクラッシュしてもファイルの場所（フォルダ＝状態）から安全に再開できる。二重処理はpHashで防ぐ。
  • モデル差し替え：モデル名・エンドポイントは設定ファイル1箇所。将来LiteLLM経由に切り替える場合もbase_url変更のみで対応可能なこと。
  • 撤退容易性：全データはSQLite1ファイル＋画像フォルダ。CSVエクスポート機能を持ち、いつでも他の家計簿アプリへ移行できる（ロックイン無し）。

テスト計画と受入基準

9-1ゴールデンセットの構築（最初の週末にやる）

  • 実レシート30枚を撮影し、正解データ（店名・日付・合計・品目）を手入力したCSVを作る。
  • 内訳を意図的に散らす：スーパー10・コンビニ5・飲食店5（手書き風含む）・ドラッグストア5・その他5。長いレシート・感熱紙の薄いやつ・くしゃくしゃのやつを必ず混ぜる。
  • 撮影条件も散らす：明るい/暗い、正面/斜め、影あり。

9-2テスト項目

試験内容合格基準
抽出精度試験ゴールデンセット30枚を流し、正解CSVと突合NFR-Q1〜Q3の達成
検証機能試験故意に壊した画像（白紙・ボケ・レシート以外の写真）を投入全件がreview/failedに落ち、confirmedに混入しない
重複試験同一レシートを2回投入・再撮影版を投入2回目がreview(重複疑い)になる
E2E試験Pixelで撮影→レポート反映まで通し無操作で60秒以内にDB登録
境界試験処理中のMac強制終了→再起動欠損・二重登録なく自動再開
通信試験処理中の外向き通信を監視（Little Snitch等）Syncthing以外の外部通信ゼロ

※ モデルやプロンプトを変えたら同じ30枚を流し直す。これが「回帰テスト」になり、性能測定手順書で作った評価の型がそのまま生きる。

リスクと対策

リスク影響対策
手書き・かすれレシートの精度不足中三値管理でreviewに落とす設計が既に対策。無理に自動化率100%を狙わない（要確認率30%以内なら成功と定義）
品目の日本語略称が解釈不能（「ｷｬﾍﾞﾂ1/2」等）小品目はv1では参考情報の位置づけ（NFR-Q3=80%）。費目はレシート単位の主費目で運用
Syncthingの同期遅延・電池消費小Wi-Fi接続時のみ同期の設定。リアルタイム性は要件でない（60秒目標はMac側処理）
モデルの世代交代（より良いVLMの登場）好機設定1箇所差し替え＋ゴールデンセット再実行で乗り換え判断が30分で可能な設計にしてある
家族の写真等、レシート以外がinboxに混入中VLMに「レシートでない場合はis_receipt=falseを返す」判定を追加し、即failedへ隔離（v1.1で対応）

用語集（初心者向け）

用語意味
VLMVision Language Model。画像を「見て」言葉で答えられるLLM。本システムの目
構造化出力LLMの返答を自由文でなくJSONスキーマ通りに強制する仕組み。Ollamaではformatパラメータ
温度(temperature)出力のランダム性。0にすると毎回同じ答えになり、抽出処理が安定する
pHash(知覚ハッシュ)画像の「見た目の指紋」。少し違う撮り直し画像も同一と判定でき、重複検出に使う
三値管理成功/失敗の二択でなく「不明(要確認)」を明示的に設ける設計。AIの不確実さを運用で受け止める要
ゴールデンセット正解付きのテストデータ集。精度を数値で語り、変更の良し悪しを判定する物差し
launchdmacOS標準のジョブ管理。フォルダ監視や定期実行をOSに任せられる(Linuxのsystemd相当)
Picker APIGoogleフォトから「ユーザーが手で選んだ写真だけ」をアプリに渡す公式API。全自動取得はできない
